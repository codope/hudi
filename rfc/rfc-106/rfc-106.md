## Abstract

On object storage (GCS, S3, ABFS) the dominant cost of small, random reads is **per-request round-trip
latency**, not bandwidth. Google recently open-sourced *GCS Analytics Core* and wired it natively into
Apache Iceberg's `GCSFileIO` (Iceberg 1.11.0), reporting large TPC-DS scan-time improvements from two
read-side optimizations: **Parquet footer prefetch** and **threaded vectored I/O** (parallel, coalesced
range reads). This RFC proposes bringing equivalent capabilities to Apache Hudi through a small, generic
extension to Hudi's storage abstraction, applied first to the read path that is **uniquely Hudi's to
optimize** — the native HFile reader behind the **metadata table** (record-level index, bloom filter,
column/partition stats) — and, in a second phase, enabling the analogous win for Parquet base/log
reads via the Hadoop FileSystem vectored-read path.

## Background

### Two read families, two mechanisms
Hudi reaches stored bytes through two distinct families, and a cloud read optimization reaches them by
different means:

1. **Parquet family (base files and Parquet log blocks).** Base-file Parquet is read by the *engine's
   own* reader (Spark `VectorizedParquetRecordReader`, Flink `ParquetSplitReaderUtil`, Trino page
   source, Hive MR) over the engine/Hadoop `FileSystem`; Parquet log blocks are read by parquet-java via
   `InLineFileSystem.open()` → outer-file `FileSystem.open()`. Neither uses Hudi's `HoodieStorage`
   seekable seam. The vectored win for this family therefore arrives through **parquet-hadoop ≥1.16
   calling `FSDataInputStream.readVectored()` on Hadoop 3.3+**, with an underlying connector that
   implements `readVectored`. Hudi already prepared the inline plumbing for this
   (`InLineFsDataInputStream`/`OffsetAdjustingStream`).
2. **HFile family (metadata table, bootstrap index, HFile log blocks).** Read by Hudi's *own* native
   HFile reader through `HoodieStorage.openSeekable(...) → SeekableDataInputStream`. parquet-hadoop is
   irrelevant here, and `SeekableDataInputStream` exposes only `seek()`/`getPos()` — **no positional or
   vectored read API**. This is the family only Hudi can optimize, and the focus of Phase 1.

### Why the HFile family matters (prize sizing)
Every metadata lookup funnels through
`HoodieBackedTableMetadata.lookupIndexRecords` → `HoodieFileGroupReader` →
`HoodieNativeAvroHFileReader.RecordByKeyIterator.seekTo(key)` (one `seekTo` per key). Metadata base
files are HFile and log blocks are `HFILE_DATA_BLOCK` (inline HFiles), so the entire metadata read
surface is HFile.

- **Record Level Index (RLI) upsert tagging** issues **O(N)** `seekTo` for N incoming keys, hashed
  across G shards. At tens-of-millions-of-rows scale the `record_index` base HFile exceeds the in-memory
  file cache (`hoodie.metadata.file.cache.max.size.mb`, default 50 MB; 100M rows / 10 file groups ≈
  480 MB), so it streams via `openSeekable` and each distinct data block a sorted key-batch touches is a
  serial `seek()+readFully()` today. This is the large, latency-bound prize.
- **A lookup is a MOR merge.** For a file slice with 1 base + D log blocks (D bounded by
  `hoodie.metadata.compact.max.delta.commits`, default 10), the lookup is **`(1+D)` opens +
  `(1+D)×|K|` seekTos**, executed sequentially with a barrier (all log blocks scanned into memory, then
  base merged). This multiplies the per-file cost by ~(1+D) between compactions.
- col_stats (2 file groups) / bloom_filters (4 file groups) are smaller, often fully buffered, and
  prefix-sequential — a comparatively minor prize, plus a block cache (`CachingHFileReaderImpl`) already
  mitigates repeat reads.

### Current gaps (evidence)
- `hudi-io/.../io/SeekableDataInputStream.java` — `seek()`/`getPos()` only; no vectored/positional reads.
- `hudi-hadoop-common/.../io/hadoop/HadoopSeekableDataInputStream.java` — wraps `FSDataInputStream` but
  surfaces nothing beyond seek/getPos; `readVectored` is the only such reference in the repo, and only in
  `InLineFsDataInputStream` (inline-Parquet prep).
- GCS streams are wrapped in `BufferedFSInputStream` (HUDI-140 EOF workaround,
  `HadoopFSUtils.getFSDataInputStreamForGCS`) which strips `PositionedReadable` on the `openSeekable`
  path.
- Default build: `parquet 1.13.1 + hadoop 2.10.2` (no vectored API). Profiles for `parquet 1.16/1.17 +
  hadoop 3.4.x` already exist.

### GCS connector reality (for Phase 2)
The Hadoop GCS connector already overrides `readVectored`, and gcs-analytics-core is integrated into the
connector on `master` (PR #1712, May 2026) but not yet in a released artifact; today gcs-analytics-core's
optimized path is reachable only via Iceberg `GCSFileIO`. parquet-hadoop calls `readVectored` from 1.14
(opt-in `parquet.hadoop.vectored.io.enabled`, default-on in 1.16) on Hadoop ≥3.3.5; Spark reaches it
through parquet-hadoop with no Spark change.

## Goals / Non-Goals

**Goals**
- A small, **cloud-agnostic** vectored/positional read capability in `hudi-io`, mirroring Iceberg's
  `SeekableInputStream` + `RangeReadable` split.
- Apply it to the **native HFile reader** (Phase 1) to cut metadata-table round trips via (a) per-stream
  load-on-open prefetch + vectored multi-block batching and (b) cross-stream parallel fan-out across the
  `(1+D)` HFiles of a MOR slice.
- A **GCS implementation** reusing gcs-analytics-core in `hudi-gcp`, pluggable via existing extension
  points; graceful fallback when absent.
- Enable the **Parquet family** vectored path (Phase 2) with minimal Hudi code.
- A reproducible **benchmark** (round-trip count primary metric) for both families.

**Non-Goals**
- No write-path changes. No change to merge semantics/correctness. No new query engine integration.
- Not coupling Hudi to GCS: GCS is the first impl of a generic seam; S3/ABFS can follow.

## Implementation

### Phase 1 — Generic seam + native HFile reader (uniquely Hudi)

**1. Generic capability in `hudi-io` (cloud-agnostic).**
Keep `SeekableDataInputStream` as the base. Add a mixin interface (working name `RangeReadable`) and a
`FileRange` value type:

```java
public interface RangeReadable {
  void readFully(long position, byte[] buffer, int offset, int length) throws IOException;
  // default: sequential per-range fallback using readFully(position, ...)
  void readVectored(List<FileRange> ranges, IntFunction<ByteBuffer> allocate) throws IOException;
}
// FileRange = (long offset, int length, CompletableFuture<ByteBuffer> result)
```

Readers detect capability: `if (stream instanceof RangeReadable) <vectored path> else <current
seek+readFully>`. This keeps every existing impl working unchanged.

**2. Implementations.**
- `HadoopSeekableDataInputStream implements RangeReadable` by delegating to
  `FSDataInputStream.readVectored` (Hadoop 3.3+) / positional `readFully`; this transparently picks up
  the GCS connector's own vectored impl when running on Hadoop 3.3+. Avoid the
  `BufferedFSInputStream` wrap on GCS where it would strip `PositionedReadable`.
- `ByteArraySeekableDataInputStream` (fully-buffered small files) serves ranges from memory.
- `hudi-gcp`: a `RangeReadable` GCS stream backed by gcs-analytics-core `GoogleCloudStorageInputStream`
  (footer prefetch + threaded vectored), surfaced via a GCS-aware `HoodieStorage`/`HoodieIOFactory`,
  pluggable through `hoodie.storage.class` / `hoodie.io.factory.class`. The gcs-analytics-core dependency
  is optional/reflectively isolated (as Iceberg does) so core has no hard GCS dependency.

**3. Native HFile reader — lever (a): per-stream prefetch + vectored batch.**
- *Load-on-open prefetch*: `HFileReaderImpl.initializeMetadata()` issues ~4 reads for a single-level
  index (trailer + root data index + meta index + fileinfo), +N for multi-level leaf index blocks. The
  region `[trailer.getLoadOnOpenDataOffset(), fileSize)` is contiguous → one `readFully` of that tail
  serves trailer+indexes+fileinfo from a buffer (≈4→1 round trip). Scattered leaf-index blocks → one
  `readVectored`.
- *Vectored multi-block lookup*: in `HoodieNativeAvroHFileReader.RecordByKeyIterator` the full sorted key
  set is known up front; map keys → the distinct set of data blocks via the in-memory
  `dataBlockIndexEntryMap`, then issue one `readVectored` for all M blocks instead of M serial
  `instantiateHFileDataBlock` → `seek()+readFully()`. Same idea for key-prefix scans.
- Both are guarded by capability detection and fall back to today's behavior.

**4. MOR merge — lever (b): cross-stream parallel fan-out.**
A slice lookup opens `(1 base + D log)` HFiles serially. Because the log blocks are independent byte
ranges and the log scan already materializes into an in-memory map before base iteration, fan the
`(1+D)` opens/lookups out in parallel at the log-scan loader
(`DefaultFileGroupRecordBufferLoader`/`LogScanningRecordBufferLoader`), collapsing the log-scan phase
from ~D·RTT to ~1·RTT. Bounded, controllable concurrency (reuse a shared pool; map naturally onto
gcs-analytics-core's thread pool). This is a follow-up to (a).

Touch points: `HoodieNativeAvroHFileReader` (RecordByKeyIterator), `HFileReaderImpl`/`HFileBlockReader`
(block reads + init prefetch), `HoodieHFileDataBlock` (inline log-block open),
`HFileReaderFactory` (openSeekable + cache), and the log-scan loader for (b).

### Phase 2 — Parquet family (mostly enablement)
Largely dependency/profile + validation, not new Hudi code:
- Build/run on `parquet ≥1.16 + hadoop ≥3.3.5` profiles (or set `parquet.hadoop.vectored.io.enabled`
  on 1.14/1.15); ensure no path strips `PositionedReadable`.
- Rely on the GCS connector's `readVectored` (and gcs-analytics-core once a connector release ships) for
  base files and Parquet log blocks; verify the inline vectored plumbing end-to-end.
- Document the supported version matrix for cloud-vectored Parquet reads.

## Rollout/Adoption Plan
- **Backward compatible.** New mixin is additive; capability detection means non-supporting streams keep
  current behavior. No on-disk format change.
- **Config-gated.** A feature flag (e.g. `hoodie.io.vectored.read.enabled`, default off initially → on
  after bake-in) plus tuning knobs (prefetch size, max merge gap/size, fan-out concurrency) mirroring
  gcs-analytics-core options. GCS impl opt-in via `hoodie.storage.class`/`hoodie.io.factory.class`.
- **No migration tooling needed.** Wins are read-side and transparent. Phase 2 requires users to run the
  parquet≥1.16 + hadoop3.3 profile to benefit.
- **Phasing:** (a) seam + HFile per-stream vectored/prefetch → (b) MOR cross-stream fan-out → Phase 2
  Parquet enablement.

## Test Plan
- **Correctness:** existing HFile/metadata/log-reader unit + functional suites must pass unchanged with
  the seam on; add tests asserting vectored and fallback paths return identical records (key lookups,
  prefix scans, MOR base+log merge).
- **Benchmark (new):** a round-trip-counting/latency-injecting `HoodieStorage` wrapper over local FS;
  **primary metric = physical read/open round-trip count** (deterministic), secondary = wall-clock with
  injected RTT. Seed with `HoodieFileSliceTestUtils.create{BaseFile,LogFile,FileSlice}`; model on
  `LSMTimelineReadBenchmark` (HFile) and `CowTableReadBenchmark` (Parquet). Headline case: large
  (>50 MB) `record_index` HFile, random sorted key batch, measuring baseline `(1+D)`-serial round trips
  vs Phase-1 (prefetch + vectored + fan-out). Analytical expectation for a single ~512 MB record_index
  HFile, 100 keys: ~112 serial round trips → ~3, i.e. ~30× fewer (RTT-bound), with a further ~(1+D)×
  improvement from cross-stream fan-out between compactions.

## Alternatives Considered
- **Hadoop-FS readVectored for HFile too (no Hudi seam).** The native HFile reader consumes
  `SeekableDataInputStream`, not `FSDataInputStream`; it cannot call Hadoop `readVectored` without a
  capability seam. A generic mixin is the minimal enabler and also lets non-Hadoop backends (Trino,
  byte-buffer) participate.
- **GCS-coupled implementation only.** Faster but not reusable and harder to land as a general Hudi
  feature; rejected in favor of a generic seam with GCS as first impl.
- **A Hudi Parquet `InputFile` bridge to route Parquet through `openSeekable`.** Unnecessary: the Parquet
  family already gets vectored reads via parquet-hadoop over Hadoop FS; duplicating that in Hudi adds
  maintenance with no clear gain.

## Risks
- gcs-analytics-core API/availability churn → isolate via reflection + fallback.
- Cross-stream fan-out concurrency must be bounded to avoid thread/connection blowup under high
  parallelism (reuse shared pools; cap concurrency).
- The 50 MB file cache + block cache already capture some wins → benchmark must target the cold/large
  regime to measure true impact and avoid over-claiming.
