# RFC-105: Lineage Reporting for Hudi

## Proposers

- @codope

## Approvers

- TBD

## Status

Issue: [HUDI-18298](https://github.com/apache/hudi/issues/18298)

JIRA: TBD

## Abstract

Apache Hudi today is opaque to dataset- and column-level lineage tooling. Spark
SQL writes to Hudi tables go through `RunnableCommand` subclasses whose source
plans are hidden from Catalyst plan walkers; path-based incremental and CDC
reads produce `LogicalRelation`s with no `catalogTable`, so consumers fall back
to the relation's class name as the dataset identifier. The same problem exists
on the Flink and Java write paths, where there is no Spark plan to walk at all.

This RFC proposes a layered approach that closes the gap end-to-end:

1. **Make Hudi plans introspectable** so existing Spark-side lineage extractors
   (OpenLineage Spark integration, Atlas, DataHub, custom analyzers) can do
   their job without compile-time coupling to Hudi internals.
2. **Capture engine-side lineage signals** (input datasets, column-level
   derivations) into a Hudi-native `LineageContext` keyed to the in-flight
   write.
3. **Define a pluggable `LineageReporter` interface** modeled on Hudi's
   existing `MetricsReporter` pattern — neutral to any specific lineage spec.
   Hudi emits a `LineageEvent` from `BaseHoodieWriteClient.commit(...)` and
   fans out to one or more configured reporters. OpenLineage, Atlas, DataHub,
   and user-defined reporters all become equal pluggable backends.

The design intentionally keeps Hudi core free of any third-party lineage
dependency. Reporter implementations live in their own optional Maven modules.

## Background

### The lineage gap today

A consumer that walks an analyzed Spark plan to extract column lineage hits
two dead ends on Hudi:

**Hudi MERGE is opaque.** `MergeIntoHoodieTableCommand` extends
`HoodieLeafRunnableCommand`, which forces `children = Nil`. That contract
exists for a good reason — it prevents Catalyst optimizer rules from rewriting
the source/target subtrees out from under Hudi's custom analysis — but it also
hides the source plan, target plan, and merge condition from every plan
walker. Lineage tooling sees a leaf node with no inputs and reports the merge
as having zero upstream columns.

The other Hudi write commands (`Insert`, `Update`, `Delete`, `CTAS`) were
migrated to `DataWritingCommand`/`UnaryCommand` in [HUDI-7915 / #12772][hudi-7915],
which exposes their source plans via standard `children`, so MERGE is the
remaining gap on the SQL write path.

[hudi-7915]: https://github.com/apache/hudi/pull/12772

**Path-based incremental and CDC reads are anonymous.** When a user runs
`spark.read.format("hudi").option("hoodie.datasource.query.type",
"incremental").load(path)`, the resulting `LogicalRelation.catalogTable` is
`None`. Lineage tooling then falls back to the relation's class name as the
dataset identifier — useless for tracking which table a query came from.

**Non-Spark engines have no lineage signal at all.** Flink writes, the Java
client, DeltaStreamer's source resolution, and table services (compaction,
clustering, rollback) all bypass Spark plan walking entirely.

### What's already in flight

[apache/hudi#18726][pr-18726] addresses the two Spark-side gaps above as a
minimal, surgical change:

[pr-18726]: https://github.com/apache/hudi/pull/18726

- `MergeIntoHoodieTableCommand.innerChildren` exposes the analyzed
  `MergeIntoTable` (source plan, target plan, merge condition, matched and
  not-matched actions) without breaking the optimizer leaf contract.
  `innerChildren` is not traversed by `transform`/`mapChildren`; it is
  consumed only by `EXPLAIN` rendering and opt-in plan walkers.
- `HoodieIncrementalRelationIdentifier`, a post-hoc analyzer rule, stamps a
  synthesized `CatalogTable` (table name, base path, schema) onto path-based
  reads whose underlying file index is `HoodieIncrementalFileIndex` or
  `HoodieCDCFileIndex`.

That PR is Layer 1 of this RFC. It is the precondition for everything else
and is being tracked separately so the foundational change can land while the
broader design here is debated.

### Why a layered design

The lineage problem has three independent dimensions:

| Dimension | Question | Answer in this RFC |
|---|---|---|
| **Visibility** | Can plan walkers see what Hudi commands wrap? | Layer 1 (innerChildren + catalogTable enrichment) |
| **Engine signal** | Where do input datasets and column mappings come from? | Layer 2 (engine-side extractors populating `LineageContext`) |
| **Emission** | Where do lineage events go? | Layer 3 (`LineageReporter` interface + reference impls) |

Each layer is independently shippable and independently valuable. A user with
an existing OpenLineage Spark agent gets value from Layer 1 alone. A user who
wants Hudi to emit lineage natively waits for Layer 3. The layers compose;
they do not block each other.

## Goals

- **G1.** Existing Spark-side lineage extractors (OpenLineage Spark
  integration, custom Catalyst walkers) work against Hudi tables without
  compile-time coupling to Hudi classes.
- **G2.** Path-based incremental and CDC reads carry the table identity
  needed for downstream lineage attribution.
- **G3.** Hudi exposes a transport- and spec-neutral `LineageReporter`
  interface so that OpenLineage, Atlas, DataHub, and user-defined backends are
  equal pluggable consumers.
- **G4.** The interface fires for *every* write that flows through
  `BaseHoodieWriteClient.commit(...)` regardless of engine (Spark SQL, Spark
  DataFrame, Flink, Java, DeltaStreamer, Kafka Connect).
- **G5.** Hudi core takes no third-party lineage dependency. All vendor
  integrations live in optional modules.
- **G6.** Reference implementation: an `OpenLineageReporter` shipped in an
  optional `hudi-lineage-openlineage` module.

## Non-Goals

- **Defining a new lineage event spec to compete with OpenLineage.**
  `LineageEvent` is the in-process Hudi-internal payload handed to reporters.
  Reporters translate it to whatever wire format their backend speaks. We do
  not claim `LineageEvent` is a public lineage standard.
- **Full Spark Catalyst-equivalent column derivation.** Layer 2 produces
  Hudi-grade column mappings (target column ← source columns + transformation
  type). Producing rich expression-trace lineage like `ColumnLineageParserV3`
  is the responsibility of the engine-side extractor; Hudi only requires that
  the engine populate the `LineageContext` with whatever fidelity it can.
- **Lineage for cleaning** (no data flow) and **archive** (no schema change).
  These can be added later if there is demand.
- **Read-side lineage emission.** This RFC focuses on writes. Read-side
  identity is solved by Layer 1 for Spark; engine-native lineage extractors
  are responsible for read-side dataset attribution.

## Design

### Layer 1 — Plan introspectability (PR #18726)

This layer is being delivered by [apache/hudi#18726][pr-18726] and is summarized
here for completeness. Two changes:

**1a. `MergeIntoHoodieTableCommand.innerChildren` override.**

```scala
case class MergeIntoHoodieTableCommand(mergeInto: MergeIntoTable)
    extends HoodieLeafRunnableCommand ... {
  override def innerChildren: Seq[QueryPlan[_]] = Seq(mergeInto)
}
```

Applied to both `hudi-spark3-common` and `hudi-spark4-common`. Preserves
`HoodieLeafLike#children = Nil` (Catalyst optimizer safety). `innerChildren`
is consumed only by `EXPLAIN` and by plan walkers that opt in.

**1b. `HoodieIncrementalRelationIdentifier` post-hoc analyzer rule.**

```scala
object HoodieIncrementalRelationIdentifier extends Rule[LogicalPlan] {
  override def apply(plan: LogicalPlan): LogicalPlan =
    AnalysisHelper.allowInvokingTransformsInAnalyzer {
      plan transform {
        case lr @ LogicalRelation(hfsr: HadoopFsRelation, _, None, _)
            if isIncrementalOrCDC(hfsr.location) =>
          val metaClient = hfsr.location.asInstanceOf[HoodieFileIndex].metaClient
          lr.copy(catalogTable = Some(buildCatalogTable(metaClient, lr.schema)))
      }
    }
  // ...
}
```

Registered via `customPostHocResolutionRules`. Scope is intentionally limited
to `HoodieIncrementalFileIndex` and `HoodieCDCFileIndex`; catalog-registered
reads already populate `catalogTable`, and snapshot path reads have a working
fallback in existing tooling.

**Why this is sufficient as a foundation.** Once these two changes land,
existing Spark-side lineage extractors that match on Spark-native types
(`MergeIntoTable`, `UpdateTable`, `DeleteFromTable`, `LogicalRelation` with a
`CatalogTable`) work against Hudi without referencing any Hudi class. This is
the unlock that makes Layers 2 and 3 architecturally clean.

### Layer 2 — Engine-side lineage capture

Layer 1 makes the data **reachable**. Layer 2 turns the reachable data into a
Hudi-native lineage signal.

**Per-engine extractor.** Each engine module ships an extractor that walks
the in-flight write's plan/operator tree and produces a `LineageContext`:

| Engine | Extractor (proposed location) | Source of signal |
|---|---|---|
| Spark SQL | `hudi-spark-common`: `HoodiePlanLineageExtractor` | walks `innerChildren` exposed by Layer 1 |
| Spark DataFrame | `hudi-spark-common`: same extractor, different entry point | the `Dataset[Row]` passed to `HoodieSparkSqlWriter.write()` |
| Flink | `hudi-flink-client`: `HoodieFlinkLineageExtractor` | Flink table-API plan / operator metadata |
| DeltaStreamer | `hudi-utilities`: existing `StreamSync` source resolution | `hoodie.deltastreamer.source.*.path` config |
| Java client | none — input datasets are user-supplied via API | caller of `HoodieJavaWriteClient` |
| Compaction / clustering | none — `inputs` is empty, operation type carries the signal | commit metadata |

**The `LineageContext` is engine-neutral.** It holds Hudi-native types only:

```java
package org.apache.hudi.lineage;

public class LineageContext {
  private final List<DatasetRef> inputs;
  private final List<ColumnMapping> columnMappings;
  private final Map<String, String> extraMetadata;
}
```

The extractor populates the context and attaches it to the write client
instance (per-write, thread-local fallback for legacy paths). The commit hook
in Layer 3 reads from this context when building the `LineageEvent`.

**Why this is engine-side, not in `hudi-common`.** The signal comes from the
engine's plan or operator graph. Putting the extractor in `hudi-common` would
either require Hudi to depend on Spark/Flink (we don't) or limit lineage to
what's already in commit metadata (which is too coarse for column-level).

### Layer 3 — `LineageReporter` interface and commit emission

This is the architectural commit of the RFC.

#### The interface

```java
package org.apache.hudi.lineage;

import org.apache.hudi.ApiMaturityLevel;
import org.apache.hudi.PublicAPIClass;
import org.apache.hudi.PublicAPIMethod;

@PublicAPIClass(maturity = ApiMaturityLevel.EVOLVING)
public interface LineageReporter {

  /**
   * Called once per successful commit, after metadata is persisted.
   * Implementations should be best-effort and must not throw.
   */
  @PublicAPIMethod(maturity = ApiMaturityLevel.EVOLVING)
  void onCommit(LineageEvent event);

  /** Lifecycle hook. Implementations release resources here. */
  default void close() {}
}
```

Direct analogue of `HoodieWriteCommitCallback`, but distinguished from it for
two reasons:

1. **Multi-instance.** Lineage typically fans out to several backends
   (e.g. OpenLineage to Marquez plus an internal catalog). The existing
   callback config (`hoodie.write.commit.callback.class`) is single-instance.
2. **Lineage-shaped payload.** The existing
   `HoodieWriteCommitCallbackMessage` carries commit time, table name, and
   write stats — enough for ack-style integrations but not for
   input-dataset/column-mapping payloads. Growing it to support lineage
   would conflate two distinct contracts.

#### The event payload

```java
@PublicAPIClass(maturity = ApiMaturityLevel.EVOLVING)
public class LineageEvent {
  /** Hudi commit instant (yyyyMMddHHmmssSSS). */
  private final String commitInstant;

  /** UPSERT, INSERT_OVERWRITE, COMPACTION, CLUSTERING, ROLLBACK, ... */
  private final HoodieOperationType operation;

  /** Always known: the table being written. */
  private final DatasetRef output;

  /** Engine-supplied. Empty for table services and Java-client writes
   *  that did not register inputs. */
  private final List<DatasetRef> inputs;

  /** Engine-supplied. Empty when the engine cannot produce column-level
   *  derivations (e.g. Flink v1, Java client, table services). */
  private final List<ColumnMapping> columnMappings;

  /** Hudi-internal extras: partition paths touched, file group ids,
   *  schema evolution version, transformer chain id, etc. */
  private final Map<String, String> extraMetadata;
}

public class DatasetRef {
  private final String name;        // table name, or path-derived identifier
  private final Optional<String> namespace;
  private final Optional<String> location;
  private final Optional<Schema> schema;
}

public class ColumnMapping {
  private final String targetColumn;
  private final List<SourceColumnRef> sourceColumns;
  private final TransformationType transformationType;
  private final Optional<String> expression; // serialized form for backends that want it
}

public enum TransformationType {
  IDENTITY, EXPRESSION, AGGREGATION, FILTER, JOIN, WINDOW, SORT, UNKNOWN
}
```

These types live in `hudi-common`. They reference no third-party lineage
spec. Reporters translate them to whatever their backend speaks (OpenLineage
`InputDatasetFacet` / `OutputDatasetFacet` / `ColumnLineageDatasetFacet`,
Atlas `EntityNotification`, DataHub `MetadataChangeProposal`, etc.).

#### Wiring into the commit lifecycle

Hook point: `BaseHoodieWriteClient.commit(...)`, after metadata is persisted
and the existing `HoodieWriteCommitCallback` fires. Hudi already has the
plumbing for "post-commit, best-effort, exceptions are logged not thrown" via
`HoodieWriteCommitCallbackUtil`; lineage emission follows the same pattern.

```java
// Inside BaseHoodieWriteClient, after commit metadata is persisted:
if (config.isLineageEnabled()) {
  LineageEvent event = lineageEventBuilder
      .withCommitMetadata(commitMetadata, instantTime)
      .withMetaClient(getMetaClient())
      .withContext(LineageContext.current(this))   // engine-supplied (Layer 2)
      .build();
  for (LineageReporter reporter : lineageReporters) {
    try {
      reporter.onCommit(event);
    } catch (Throwable t) {
      LOG.warn("Lineage reporter {} failed; continuing", reporter, t);
    }
  }
}
```

#### `LineageReporterFactory` and configuration

Mirrors `MetricsReporterFactory`. Reporters are instantiated by class name
from a comma-separated config:

```properties
# Master switch.
hoodie.lineage.enable=true

# Comma-separated list of fully-qualified reporter class names.
hoodie.lineage.reporters=\
  org.apache.hudi.lineage.openlineage.OpenLineageReporter

# Per-reporter config follows the reporter's own prefix.
hoodie.lineage.openlineage.transport.type=http
hoodie.lineage.openlineage.transport.url=http://marquez.local:5000
hoodie.lineage.openlineage.namespace=production-warehouse
```

Each reporter declares its own config prefix and is responsible for parsing
its own subtree of `hoodie.lineage.<vendor>.*`. Hudi core knows nothing about
any specific vendor's config schema.

### Module layout

| Module | New / existing | Contents | Dependencies |
|---|---|---|---|
| `hudi-common` | existing | `LineageReporter` interface, `LineageEvent`, `DatasetRef`, `ColumnMapping`, `TransformationType` | none |
| `hudi-client-common` | existing | `LineageReporterFactory`, `LineageContext`, lineage-config classes, wiring into `BaseHoodieWriteClient.commit(...)` | `hudi-common` |
| `hudi-spark-common` | existing | `HoodiePlanLineageExtractor` (consumes Layer 1's `innerChildren`); per-write context attachment | `hudi-client-common`, Spark |
| `hudi-flink-client` | existing | `HoodieFlinkLineageExtractor` (operator-level capture) | `hudi-client-common`, Flink |
| `hudi-utilities` | existing | DeltaStreamer integration: populate `LineageContext` from `srcIdOpt` resolution | `hudi-client-common` |
| `hudi-lineage-openlineage` | **new** | `OpenLineageReporter` reference impl | OpenLineage Java client |
| `hudi-lineage-atlas` | future | `AtlasLineageReporter` | Atlas client |
| `hudi-lineage-datahub` | future | `DataHubLineageReporter` | DataHub emitter |

The OpenLineage reporter ships with the RFC. Atlas / DataHub modules are
listed as future work to demonstrate the pattern is genuinely pluggable — they
can be contributed by interested parties without touching Hudi core.

### End-to-end flow (Spark SQL `MERGE INTO`)

```
USER: MERGE INTO target USING source ON ... WHEN MATCHED THEN UPDATE ...
  │
  ▼
Spark parser → MergeIntoTable (Catalyst node)
  │
  ▼
HoodieAnalysis rule rewrites to MergeIntoHoodieTableCommand(mergeInto)
  │  ── Layer 1 (PR #18726) ──
  │  innerChildren = Seq(mergeInto)        ← visible to plan walkers
  │  catalogTable populated on incremental sources
  ▼
HoodieSparkSqlWriter / write client
  │  ── Layer 2 ──
  │  HoodiePlanLineageExtractor walks cmd.innerChildren:
  │    inputs       ← mergeInto.sourceTable.collectLeaves()
  │    columnMaps   ← mergeInto.matchedActions.flatMap(_.assignments)
  │  Attaches LineageContext to write client.
  ▼
BaseHoodieWriteClient.commit(...)
  │  Persists commit metadata.
  │  Fires existing HoodieWriteCommitCallback (unchanged).
  │  ── Layer 3 ──
  │  Builds LineageEvent { commitInstant, UPSERT, output=target,
  │                        inputs=[source], columnMappings=[...] }
  │  Fans out to each configured LineageReporter.
  ▼
OpenLineageReporter.onCommit(event)
  │  Translates to OpenLineage RunEvent + ColumnLineageDatasetFacet
  │  Posts to Marquez / configured transport.
  ▼
Marquez / DataHub / Atlas / etc.
```

For Flink writes: Layer 1 does not apply (no Spark plan), but Layer 2's
`HoodieFlinkLineageExtractor` populates the same `LineageContext` from the
Flink operator graph, and Layer 3 fires identically.

For compaction / clustering: Layers 1 and 2 do not apply.
`LineageContext.inputs` is empty. `LineageEvent.operation` is `COMPACTION` /
`CLUSTERING`. Reporters can choose to emit a self-loop or skip.

## Alternatives Considered

### A. Reuse `HoodieWriteCommitCallback`

Instead of a new interface, extend `HoodieWriteCommitCallbackMessage` with
input-dataset and column-mapping fields.

- **Pro:** one fewer interface; reuses existing wiring.
- **Con:** single-instance config; conflates lineage with general post-commit
  notifications; bloats a public API with lineage-specific concepts.

**Rejected.** The single-instance limitation is the blocker. Lineage routinely
fans out to multiple backends.

### B. Hudi natively emits OpenLineage events

Skip the neutral interface and have Hudi core depend on the OpenLineage Java
client directly.

- **Pro:** less indirection; one canonical event format.
- **Con:** Hudi takes a hard dependency on OpenLineage; users who run Atlas
  or DataHub still have to translate; couples Hudi's release cadence to OL's
  spec evolution.

**Rejected.** Hudi already uses the neutral-reporter pattern for metrics
(`MetricsReporter` → `JmxMetricsReporter` / `DatadogMetricsReporter` /
`PrometheusMetricsReporter` / etc.). Lineage should follow the same precedent.

### C. Pure plan-walking, no Hudi-side reporter

Rely entirely on Layer 1 + an external lineage agent (e.g. OpenLineage Spark
agent) to walk plans and emit events.

- **Pro:** no new code in Hudi beyond #18726.
- **Con:** does not cover Flink, Java, DeltaStreamer, table services; column
  derivations from `MergeIntoTable.matchedActions` are clean but column
  derivations from a Hudi compaction are simply absent because there is no
  plan to walk.

**Rejected as the sole solution.** This is a useful adjunct (Layer 1 is
exactly this) but does not close the gap end-to-end.

### D. Lineage contract trait in the engine

A trait like `trait LineageProvider { def sourceTablePlans: Seq[LogicalPlan];
def targetTableIdentifier: Option[TableIdentifier] }` implemented by Hudi
commands.

- **Pro:** compile-time-safe contract.
- **Con:** lives only in a forked Spark; OSS-incompatible; over-engineered
  when `innerChildren` already provides the same access through a standard
  Spark API.

**Rejected.** Layer 1's `innerChildren` solves the same problem with zero new
interfaces and zero compile-time coupling to Hudi from the Spark side.

## Rollout / Adoption Plan

The RFC ships in stages. Each stage is independently useful and independently
revertable.

### Phase 1 — Foundation (PR #18726, in flight)

- `innerChildren` on `MergeIntoHoodieTableCommand` (spark3-common, spark4-common)
- `HoodieIncrementalRelationIdentifier` analyzer rule
- Tests under `hudi-spark/src/test/scala/.../analysis/`

**User impact:** none on writes; `EXPLAIN` output now shows the inner
`MergeIntoTable`; existing Spark-side lineage extractors that handle
`MergeIntoTable` start producing edges for Hudi merges.

### Phase 2 — Interface + wiring (no reporter impls)

- `LineageReporter` interface, `LineageEvent`, `DatasetRef`, `ColumnMapping` in
  `hudi-common`
- `LineageReporterFactory`, `LineageContext`, lineage configs in
  `hudi-client-common`
- Hook into `BaseHoodieWriteClient.commit(...)`
- A trivial `LoggingLineageReporter` impl for testing

**User impact:** none unless `hoodie.lineage.enable=true`. With the flag on
and only `LoggingLineageReporter` configured, lineage events appear in the
driver log.

### Phase 3 — Spark extractor

- `HoodiePlanLineageExtractor` in `hudi-spark-common` consuming Layer 1's
  `innerChildren`
- DataFrame-API entry point (extracts from the `Dataset[Row]` passed to the
  writer)

**User impact:** Spark write paths now populate `LineageContext` → Phase 2
events carry inputs and column mappings.

### Phase 4 — OpenLineage reference reporter

- New `hudi-lineage-openlineage` optional Maven module
- `OpenLineageReporter` translating `LineageEvent` → OpenLineage `RunEvent`
- Bundle published alongside other Hudi bundles

**User impact:** users add the bundle and configure
`hoodie.lineage.reporters=org.apache.hudi.lineage.openlineage.OpenLineageReporter`.

### Phase 5 — Flink extractor and DeltaStreamer integration

- `HoodieFlinkLineageExtractor`
- DeltaStreamer populates `LineageContext` from the source resolution it
  already does
- Per-engine docs

### Phase 6 — Community-contributed reporters

- `hudi-lineage-atlas`, `hudi-lineage-datahub`, others as the community needs
- Contributed independently against the stable Phase 2 interface

### Backwards compatibility

- `hoodie.lineage.enable` defaults to `false`. No behavior change for existing
  users until they opt in.
- `HoodieWriteCommitCallback` is unchanged. Users who already have a
  callback wired up are unaffected.
- The `LineageReporter` interface is marked `EVOLVING` until Phase 4 ships and
  has been stable through one minor release; then it is promoted to `STABLE`.

## Test Plan

### Layer 1 (PR #18726, complete)

- `TestMergeIntoHoodieTableCommandInnerChildren`:
  - Asserts the leaf contract (`children.isEmpty`) is preserved
  - Asserts `innerChildren` exposes the analyzed `MergeIntoTable` with
    reachable source/target leaves and assignments
  - Asserts `EXPLAIN` round-trip shows the source view name
- `TestHoodieIncrementalRelationIdentifier`:
  - Path-based incremental read (parameterized over COW / MOR) populates
    `catalogTable`
  - Catalog-registered incremental read is unchanged
  - Snapshot path read is not enriched (scope guard)

### Layer 2

- `HoodiePlanLineageExtractor` unit tests against fixture plans for
  `MergeIntoTable`, `UpdateTable`, `DeleteFromTable`, `InsertIntoStatement`
- Integration test: full Spark SQL `MERGE INTO` flow produces a
  `LineageContext` with the expected inputs and column mappings

### Layer 3

- `LineageReporterFactory` unit tests for class loading, config parsing,
  multi-reporter fan-out, and exception isolation
- `BaseHoodieWriteClient.commit(...)` integration test asserting:
  - With `hoodie.lineage.enable=false`, no reporter is invoked
  - With multiple reporters configured, each is invoked exactly once per
    commit
  - A throwing reporter does not break the commit or prevent other reporters
    from firing
- `OpenLineageReporter` end-to-end test against a Marquez container in CI

### Cross-engine

- Spark SQL: `INSERT`, `MERGE INTO`, `UPDATE`, `DELETE`, `CTAS` each emit a
  well-formed `LineageEvent`
- Spark DataFrame: `df.write.format("hudi").save(path)` emits with inputs
  derived from the `Dataset`
- Flink (deferred to Phase 5): basic INSERT-table emits with inputs derived
  from the source operator
- Compaction / clustering: emits with empty `inputs` and the right operation
  type

## Open Questions

1. **`LineageEvent` payload shape.** Are the proposed fields the right
   first-class set, or are there Hudi-specific facets (partition path
   touched, file-group-level changes, instant action ordering for OCC) that
   should be promoted from `extraMetadata` to first-class?
2. **Async vs. sync emission.** Should reporters be invoked inline on the
   commit thread, or via an async queue (similar to the existing async metrics
   reporter)? Inline is simpler; async protects commit latency from a slow
   backend.
3. **Pre-commit "intent" hook.** Some lineage systems want an intent event
   before the commit so they can reconcile against the actual commit. This
   would be a second method on `LineageReporter`. Worth adding now (cheap to
   add later, hard to remove)?
4. **Schema evolution facets.** When a write evolves the schema, should the
   new columns be tagged with a "schema evolution" relationship in the
   `ColumnMapping`, or is that the reporter's responsibility to derive from
   the schemas in `DatasetRef`?
5. **Flink lineage fidelity.** Flink's table-API plan exposes column-level
   information for some operators but not all. What is the minimum bar for
   Phase 5 — dataset-level only, or column-level where available?
6. **Bundle layout.** Should `hudi-lineage-openlineage` be a standalone bundle
   or shaded into existing engine bundles (`hudi-spark-bundle`,
   `hudi-flink-bundle`)? Shading simplifies deployment but blurs the
   "optional, no-OL-dep-by-default" boundary.
7. **Maintainer ownership.** Who in the Hudi community owns the
   `hudi-lineage-openlineage` module long term? Reference modules without an
   owner tend to rot.
